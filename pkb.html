知识库自动巡检工具

2026.09 — 至今 ｜ 独立承接 ｜ Python + 正则 / YAML 校验

一句话：知识库的损坏是静默的——肉眼看不见、diff 也看不见，只有被别的工具消费时才暴露。
所以做一个能定期扫、扫完能修、修完能复核的东西。

背景：怎么发现这类「静默损坏」

起因很具体：一次把笔记导出成 PDF 时，工具直接报 YAML 解析失败。查下去发现库里有 28 个文件的 frontmatter 写法不合法—— 而 Obsidian 对它宽容，所以平时完全看不出来。同类问题还有：双反斜杠写进链接（会静默失效）、死链、孤立笔记。 它们的共同点是：不报错，直到某个环节被别的工具消费。

我做了什么

  1. 先定位整类问题，而不是修单点：不满足于"修好这一个文件"，而是先扫全库量出波及面——828 篇 → 命中 28 个文件 / 47 处。
  2. 识别出三个变体：① 双引号里含反斜杠（YAML 双引号会处理转义，`\0` 等非法）② 裸 wikilink（被当成 flow sequence）③ 反斜杠游程 >1（链接静默失效）。
  3. 写成可重复跑的巡检 + 修复：一次扫描输出三类问题（死链 / 非法 YAML / 孤立笔记），配修复脚本，修完自动复核。
  4. 逐文件备份再改：修复前逐个文件备份，保证可回滚。
  5. 复查到 0：修复后全库复扫——344 篇合法，剩下 3 个"失败"经核对是模板里的占位符（本就该那样，不是缺陷）。

关键取舍

为什么不写一个"更宽容的解析器"绕过去？
因为问题不在解析器，在我家文件的写法不符合标准。绕过去只是把问题藏起来——下次换任何一个标准工具还会炸。修数据，而不是改判据。

为什么连"模板占位符"也要查清、而不是一起"修"？
3 个文件复扫仍失败，看着像没修干净。查清后发现是模板里的 {{date}} 占位符——模板本来就该这样。如果不查就"顺手修掉"，反而破坏了模板。

结果

一次扫描 828 篇 修复 28 个文件 / 47 处 死链 353 → 0 复扫 344 篇合法

说明：以上数字均来自本机实测输出，可复跑复核。

如果重做，我会改什么

  • 把巡检挂成定时任务。现在是手动跑——应该在每次库维护后自动跑一次，问题就不需要靠"哪天恰好用到才发现"。
  • 把判据固化进写入环节。事后扫描是补救；更彻底的是写入时就拦（例如写文件前自动规范化链接），从源头不让问题产生。
  • 补一类检查。目前只查三类；"同一概念多种叫法"这类语义问题还查不到，需要和术语表联动。
