离线自测 15 个场景全对，线上零防护：一次读错字段名的排查

2026-09 ｜ 工程可靠性 / 安全边界 ｜ 阅读约 7 分钟

一句话结论：离线自测通过 ≠ 线上生效。 我用自己造的 payload 测了 15 个场景，全对；真实环境里规则一条都没命中。 根因不是逻辑写错，是我把字段名猜错了——而这类错误的方向往往是「更宽松」： 读不到数据 → 不匹配 → 落到默认放行 → 表面全绿、实际零防护。

背景

我本地有一个 Markdown 笔记库，日常用 CLI agent 读写。为了防止误删， 给 agent 的 pre_tool_call 钩子（工具执行前触发）写了一条边界规则： 命中「删除 / 改名笔记库文件」的命令就直接拒绝执行。

写完做了自测：离线合成 payload，跑 15 个场景——普通删除、通配符删除、 改名、移动、大小写变形、路径穿越……全部按预期拦下了。钩子注册正常、 白名单配好、官方的 doctor 自检全绿。

结论：装好了。然后我把它当成了已生效。

三天后

一次真实会话里，我让 agent 执行一条删除命令，想看它被拦下来的样子。

命令照跑了。

翻钩子日志：那一刻的 6 次调用，行为全是 allow。 钩子确实在跑，只是每次都说「放行」。

排查：第一件事不是改逻辑

当时的诱惑是回去读自己的匹配逻辑，怀疑正则写漏了某种情况。 但更值得先问的是：钩子到底收到了什么？

所以没动逻辑，先在钩子入口加了一行日志，把原始 payload 的键名打出来：

log(f"RAW keys={sorted(payload.keys())}")

下一次触发，日志给出了答案：

payload keys = ['cwd', 'extra', 'hook_event_name',
                'session_id', 'tool_input', 'tool_name']

参数键叫 tool_input（Claude-Code 风格的事件结构）。 而我代码里读的是 args。

链路一下就连起来了：

  1. 读 args → 永远是 None；
  2. 拿不到命令文本 → 所有匹配规则都不成立；
  3. 规则都不成立 → 落到默认分支 allow；
  4. 于是每一次都放行，而且每一次都记了一条「正常处理」的日志。

这就是它难被发现的原因：它不报错。整条链路上没有任何异常， 自检工具看到的是「钩子已注册、返回格式合法」——全绿。

修复

  1. 改成读 tool_input，保留 args 作为回退（兼容不同版本的事件结构）。
  2. 把原来那 15 个离线用例换成正确键再跑一遍——这次是真的在测逻辑了。
  3. 回真实会话复验：删除命令被 harness 在执行前拦下，返回拒绝信息； 正常读文件照常放行。
  4. 验完删掉那行 dump 日志——payload 里可能带正文内容，不该长期落盘。

三条留下的原则

① 第一次失败时，先 dump 数据结构，别改逻辑。
用自己造的数据测自己的代码，测的是「我以为的接口」。真实的接口长相是外部事实， 只能从外部观察。一行 keys() 日志就能终结几小时的猜测。

② 注意错误的「方向」。
同样一个字段名写错，方向可能相反：
· 读不到数据 → 判为不安全 → 拒绝一切 → 你立刻会发现；
· 读不到数据 → 判为无风险 → 放行一切 → 你永远发现不了。
第二种才是真正危险的那类 bug。

③ 「读不到数据」不能等于「没问题」。
任何安全判定里，取不到输入都该按最严处理（fail closed）， 或者至少明确报出来——而不是安静地走默认分支。 默认值选错一次，整套防护就是装饰品。

泛化：还有哪些地方是同一个坑

  • Webhook / 事件回调：平台改了字段名或包了一层 data，你的解析拿到 None，然后按默认逻辑继续跑。
  • 第三方 API 响应：字段是 result 还是 data.items？猜错就返回空列表，页面显示「暂无数据」——看起来像业务正常。
  • 中间件 / 拦截层：任何「拿不到参数就跳过校验」的写法，都是同一类漏洞。
  • CI 里的守卫脚本：读不到被改动的文件列表 → 判定「无需检查」→ 直接过。

共同点：外部给我的数据结构，键名必须先看，不能先猜。自己定义、自己消费的数据不在此列（键一定对得上）。

一句话记住：当校验层「跑通了」但你不确定它真的在拦，就去数它的拒绝次数。 一次都没拒绝过的安全规则，和没装是一样的——而它给你的安心感是假的。
